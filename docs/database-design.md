# Database Design

The same schema runs on **SQLite (local mode)** and **Supabase Postgres
(cloud mode)** — only `DATABASE_URL` changes. All DDL is generated by
SQLAlchemy from `backend/models/__init__.py`.

## Entity-relationship overview

```text
┌──────────┐ 1:1  ┌──────────┐
│  users   ├──────┤ profiles │
└────┬─────┘      └──────────┘
     │ 1:N                      1:N
     ├──────────────┬─────────────────────┐
     ▼              ▼                     ▼
┌────────────┐              ┌────────────┐
│ diet_plans │              │ user_files │──► object storage (bytes)
└────────────┘              └────────────┘    (bucket / uploads folder)
```

## Tables

### `users`
| Column | Type | Constraints |
|---|---|---|
| id | VARCHAR(32) | **PK**, UUID hex |
| name | VARCHAR(120) | not null |
| email | VARCHAR(255) | **UNIQUE, INDEXED** — lookup key for login |
| password_hash | VARCHAR(255) | bcrypt hash — never the raw password |
| created_at | TIMESTAMPTZ | default now() |

### `profiles` — 1:1 with users
| Column | Type | Constraints |
|---|---|---|
| id | VARCHAR(32) | PK |
| user_id | VARCHAR(32) | **FK → users.id, UNIQUE, INDEXED** |
| age | INTEGER | 10–100 (app-enforced) |
| height_cm | INTEGER | 100–250 |
| weight_kg | INTEGER | 25–300 |
| activity_level | VARCHAR(30) | sedentary\|light\|moderate\|active\|athlete |
| dietary_preference | VARCHAR(30) | vegetarian\|vegan\|non_vegetarian\|eggetarian |
| goal | VARCHAR(30) | weight_loss\|weight_gain\|maintenance\|fitness |
| allergies | VARCHAR(255) | comma-separated known tags ("" if none) |
| meals_per_day | INTEGER | 1–6 |
| updated_at | TIMESTAMPTZ | auto-update |

### `diet_plans` — 1:N with users
| Column | Type | Constraints |
|---|---|---|
| id | VARCHAR(32) | PK |
| user_id | VARCHAR(32) | **FK → users.id, INDEXED** |
| title | VARCHAR(160) | |
| breakfast / lunch / snack / dinner | TEXT | meal descriptions |
| nutrition_summary | JSON | {calories_kcal, protein_g, carbs_g, fat_g, hydration_reminder, …} |
| engine_used | VARCHAR(30) | rule_based \| ai_api — provenance of the plan |
| goal, dietary_preference | VARCHAR(30) | snapshot of the inputs used |
| created_at | TIMESTAMPTZ | default now() |

### `user_files` — 1:N with users (metadata ONLY)
| Column | Type | Constraints |
|---|---|---|
| id | VARCHAR(32) | PK |
| user_id | VARCHAR(32) | **FK → users.id, INDEXED** |
| filename | VARCHAR(255) | original name (display) |
| storage_path | VARCHAR(500) | object key: `meals/{user_id}/{uuid}_{safe_name}` |
| content_type | VARCHAR(100) | MIME |
| size_bytes | INTEGER | |
| uploaded_at | TIMESTAMPTZ | default now() |

## Design decisions worth defending in a viva

1. **UUID surrogate keys** — no auto-increment guessing across a distributed
   cloud DB; ids can be generated by any app instance without coordination.
2. **Index every `user_id`** — "all rows for one user" is the hottest query
   (lists, dashboards, isolation checks); indexes keep it O(log n) at scale.
3. **Unique FK on `profiles.user_id`** — enforces the 1:1 relationship at the
   database level, not just in application code.
4. **`nutrition_summary` as JSON** — a flexible, schema-light blob that varies
   by engine (rule-based adds hints/BMI, AI may add notes). Relational for
   identity/ownership, document-style for engine payloads.
5. **`engine_used` provenance column** — makes the AI-vs-fallback story
   *auditable*: every saved plan records which engine produced it.
6. **Files: metadata in DB, bytes in object storage** — databases optimize for
   structured queries, not multi-MB blobs. Object storage is cheaper, scales
   to petabytes, and serves via signed URLs/CDNs. This separation is the
   classic cloud-architecture answer.
7. **`ON DELETE CASCADE`** — deleting a user removes their profile, plans and
   file metadata (object cleanup is handled by the storage layer), which keeps
   "right to be forgotten" flows trivial.

## Sample SQL (Postgres)

```sql
-- user-specific plan listing (the hottest query):
SELECT id, title, breakfast, lunch, snack, dinner,
       nutrition_summary, engine_used, created_at
FROM diet_plans
WHERE user_id = $1          -- uses index idx (user_id)
ORDER BY created_at DESC;

-- isolation by construction:
-- every query in the API filters by the JWT-derived user_id, so a forged or
-- foreign id simply matches zero rows -> 404.
```

## User-specific access model

| Question | Answer |
|---|---|
| Who can read a plan row? | only the row's `user_id` (matches the JWT `sub` claim) |
| Who can read a file's bytes? | only the owner of the `user_files` metadata row |
| What does a foreign id return? | `404` — identical to "does not exist" (no enumeration) |
| Where is this enforced? | SQL `WHERE user_id = :jwt_sub` on **every** query — not in the UI |
